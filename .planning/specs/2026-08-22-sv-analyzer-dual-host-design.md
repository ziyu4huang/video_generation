# sv-analyzer dual-host (DSH + s2-agent) — design

**Date:** 2026-08-22 · **Status:** implemented

## Problem

`dsh-plugin/sv-analyzer/` is a self-contained Verilog/SystemVerilog analyzer
(two tree-sitter grammars, one `wasm32-wasip1` binary) that today serves only
the DeepSeek Harness as a Cordis bundle. The user wants the same analyzer
available to `s2-agent.sh`, and the s2-agent devops deploy (`s2-agent-ext-
devops` deploy-cli) must ship it like any other `s2-agent-ext-*` package.

## Solution

New package `bun-apps/s2-agent-ext-sv-analyzer/` — the s2-agent face of the
analyzer. Registry entry `sv-analyzer` (`load: static`, `deploy: { order: 170,
copy: [wasm] }`). The devops deploy bundles `extensions/sv-analyzer.ts` into
`ext/sv-analyzer/ext.cjs`, copies `wasm/` beside it, and the bundle locates the
binary at runtime via the `#pi/ext-dir` loader idiom (same relocatable pattern
as archify's `vendored/`).

## Decisions

- **D1 — one Rust core, two wasm copies, synced by build.sh.** The Rust crate
  in `dsh-plugin/sv-analyzer/rust/` stays the single source of truth.
  `dsh-plugin/sv-analyzer/build.sh` mirrors the freshly built
  `plugin/wasm/sv-analyzer.wasm` into `bun-apps/s2-agent-ext-sv-analyzer/wasm/`
  (new `step_mirror_s2_ext`). Both hosts ship the same binary. The mirror is
  **gitignored, never committed** — a regenerated artifact, same policy as the
  plugin's own `plugin/wasm/` (its `.gitignore`: "regenerated by ./build.sh …
  a fresh clone runs ./build.sh first"). Operator instruction 2026-08-22:
  "don't commit files that can be regenerated, such as wasm"; the earlier
  draft's "committed like archify's vendored/" precedent does not hold —
  archify's vendored/ is all small text/assets (LICENSE, SKILL.md, schemas,
  templates), not a 40 MB binary. Consequences accepted: a fresh clone runs
  build.sh before deploy/test; the extension's wasm-dependent test layers skip
  when the wasm is absent and fail on a stale one when present.
- **D2 — no worker thread in s2-agent.** The DSH plugin runs parses on a
  worker thread because its host is a long-lived server with a UI event loop.
  s2-agent is a CLI process where a tool call blocking its own process for a
  bounded parse (≤1 MiB source, ~300 ms worst case) is the normal shape. The
  extension runs the same WASI instance inline, lazily compiled on the first
  tool call (which also keeps the enabled path IO-free for the
  extension-isolation-contract STANDALONE LOAD gate).
- **D3 — `node:wasi` works under Bun.** Verified empirically (Bun 1.4): the
  same `createAnalyzer` loader (alloc/run/response_len/free_response/dealloc
  over linear memory) runs unchanged. Bun's cjs bundler normalizes
  `node:wasi` → bare `require("wasi")`, which was missing from the core's
  builtin catalog (`src/sh/host-modules.ts` BUILTINS) — the deploy's Gate 2
  loadProbe caught it (`bundle required non-host module "wasi"`); fixed by
  adding `wasi` to BUILTINS. This is the exact class of defect the deploy
  gates exist to catch.
- **D4 — devops changed-packages alias.** `dsh-plugin/sv-analyzer/` was
  matrix-irrelevant (standalone project). Now that its wasm mirrors into a
  bun-apps package, a rust-core change must re-run `s2-agent-ext-sv-analyzer`'s
  gates: the prefix is aliased to that package via `CHANGED_FILE_ALIASES` in
  `changed-packages.ts` — a first-class directlyTouched edge (with reverse
  dependents), never a fail-open; a stale workspace without the alias package
  still fails open.
- **D5 — tool parity.** Same tool names/schemas (`sv_analyze`, `sv_ast`;
  `code`/`file`/`dialect` (+`include_ast`)) and the same render caps (1 MiB
  source, 256 KiB render) as the DSH plugin. `file` reads resolve against
  `ctx.cwd` (s2-agent has no sandbox fs service; the harness-level sandbox
  story is tool-gate). `BUN_PI_SV_ANALYZER=0` is the symmetric full-disable
  knob every base-set extension honors.

## Verification (measured)

- Extension: 14/14 bun tests pass; `tsc --noEmit` clean (package + s2-agent).
- Workspace gates: extension-isolation-contract (incl. sv-analyzer STANDALONE
  LOAD + DISABLE), dep-guard, extension-entry-typechecked, registry-freshness,
  manifest-consistency, registry-base-set — all green.
- Full `bun test` in s2-agent (1042 pass) and s2-agent-ext-devops (737 pass).
- **Full deploy to a temp outRoot**: all six build gates pass; post-deploy E2E
  verdict `pass` — boot, ext-load (17 extensions incl. sv-analyzer), and a
  real model call through the compiled binary. Deployed
  `ext/sv-analyzer/{ext.cjs,ext.json,wasm/sv-analyzer.wasm}` byte-identical to
  the plugin's wasm (single sha).
- Pre-existing failures confirmed unrelated: 7 cwd-dependent tests
  (ultracode workflow-pack / reference-pack, knowledge-card converge) fail
  identically on the pristine tree.
