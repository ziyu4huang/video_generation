## Problem Statement

When I run subagents in the pi TUI, every line the subagent display shows me is truncated at fixed character counts that have nothing to do with my terminal. On a wide terminal the live header (`subagent ▸ default ▸ glm-5.3 ▸ "You are a DevOps finish agent. Repo worktree: /Users/huangz…"`) stops at 60 characters, the running-tool line (`→ Running: git -C /Users/…`) stops at 50, the message quote stops at 80 — I get ellipses while half my screen sits empty. On a narrow terminal the same fixed cuts can overrun the real edge. If I resize the window mid-run, nothing re-flows. Text I write in Chinese or Japanese is mis-measured (each CJK character occupies 2 terminal columns but is counted as 1), so CJK lines overflow or cut in the wrong place. And when a subagent finishes, its report is dumped as raw markdown — I see literal `## (A)…` and `**bold**` markers instead of the styled headings and bold the host chat shows me for every other message.

## Solution

Every subagent display line becomes terminal-width-aware: the inline live view (header, running-tool line, progress line, message quotes, settled collapsed summary), the batch header preview, and the bottom-panel background-runs rows all truncate by real terminal columns — using the full width on wide terminals, protecting the edge on narrow ones, and re-flowing automatically when the terminal is resized. Truncation is measured with East-Asian-aware column utilities, so CJK text renders correctly everywhere. When a subagent settles, the expanded report renders as styled markdown through the same component and theme the host chat uses, so finished reports read like first-class chat messages. Streaming partials stay exactly as they are — plain capped text with the 16-line tail cap — preserving the anti-flicker fix. All of this is built from utilities and components already in the dependency graph: zero new packages.

## User Stories

1. As a pi user watching a subagent run, I want the live header line (`subagent ▸ tier ▸ model ▸ "task intent…"`), so that on a wide terminal I read far more of the task intent than today's hardcoded 60 characters allow.
2. As a pi user watching a subagent run, I want that same header protected at the real edge on a narrow terminal, so that lines never overflow, wrap mid-line, or collide with the window edge.
3. As a pi user who resizes the terminal mid-run, I want every subagent line — header, running-tool line, progress line, message quotes, settled summary — to re-flow at the new width on the next frame, so that resizing never leaves stale overlong lines.
4. As a pi user, I want the settled collapsed one-liner to use a width-derived cap instead of the hardcoded 60 columns, so that summaries fill the line on wide terminals and stay inside the edge on narrow ones.
5. As a pi user watching tool activity, I want the running-tool line (`→ Running: git -C …`) to show as much of the command as my terminal and the phrase cap allow, so that long paths and flags stay readable on wide terminals.
6. As a pi user watching tool activity, I want trace lines (`→ / ✓ / ✗ …`) truncated by column width instead of a bare 200-character slice, so that very long entries cut cleanly with an ellipsis at the real edge.
7. As a pi user, I want the last-message quote line (`↳ "…"`) under live rows to be width-aware, so that quoted prose fills the available width rather than stopping at 80 characters.
8. As a pi user, I want the progress line's activity snippet (last assistant prose in `↳ …`) to be width-aware and to end with a proper ellipsis when cut, so that I can always tell when truncation happened.
9. As a pi user writing tasks or receiving reports in Chinese, Japanese, or Korean, I want every truncation measured in terminal columns with East-Asian width rules, so that 2-column CJK characters never overflow their line or get mis-counted.
10. As a CJK-writing pi user, I want the ellipsis placed by column budget, so that a capped line of CJK text ends cleanly with a single trailing ellipsis regardless of script mix.
11. As a pi user reading a finished subagent report, I want the settled expanded result rendered as styled markdown — headings, bold, emphasis, code, theme colors — so that it reads like a host-chat message instead of raw `##` and `**` markers.
12. As a pi user reading a finished report, I want the markdown body to wrap and re-flow at my terminal width, so that long paragraphs use the full screen and re-wrap on resize.
13. As a pi user, I want the settled result's header (badge plus model/elapsed/tags meta) to keep its current shape while the body upgrades to markdown, so that recognition and my existing greps keep working.
14. As a pi user watching a still-running subagent, I want streaming partials to remain plain capped text with the 16-line expanded tail cap and the fixed 2-line collapsed shape untouched, so that the anti-flicker behavior (issue #1104) is fully preserved.
15. As a pi user, I want the header's `▸`-joined segment structure (tier slot, model segment, intent quote, segment-omission rules) unchanged, so that display conventions and pinned tests keep their meaning.
16. As a pi user dispatching a batch of subagents, I want the batch header's first-task preview to be width-aware, so that multi-subagent headers fit my terminal instead of ellipsizing at a fixed length.
17. As a pi user with subagents running in the background, I want the bottom-panel background-runs rows to consume the width they are already handed (instead of discarding it), so that row detail and latest-action text re-flow with my terminal.
18. As a pi user with background runs, I want the live-message quote lines in the bottom panel to be width-aware too, so that the whole section re-flows consistently.
19. As a pi user reviewing runs in the detached subagents viewer, I want its rows built from the same width-aware helpers, so that nested fixed-cap leftovers (running-row fallback detail, row tails) stop undercutting the viewer's own width handling.
20. As a repo maintainer, I want this effort to add zero new dependencies — reusing the terminal-UI width utilities, markdown component, and theme already in the dependency graph — so that install size and supply-chain surface stay unchanged.
21. As an extension maintainer, I want new width parameters to default to today's constants, so that every existing caller and its pinned tests keep passing, with width-awareness layered on only where a width is genuinely available.
22. As a pi user on an ultra-narrow terminal, I want truncation to degrade gracefully to a clean short line rather than crash or render empty, so that extreme window sizes cannot break the display.

## Implementation Decisions

1. **Width-aware pure render layer.** The pure render functions in the subagent render module — `taskPreview`, `workIntentPreview`, `describeLastActivity`, `latestMessageLine`, `formatHistoryLine`, `renderSubagentCall`, `renderSubagentResult` — gain an explicit width parameter. All character-count slicing (`slice(0, n)` + ad-hoc `"…"` appends, including the two bare no-ellipsis slices in the activity snippet and history text branch) is replaced by the terminal-UI column utilities (`truncateToWidth`, `visibleWidth`, `sliceByColumn` as needed). Existing constants (80, 60, 200) survive **as upper bounds**: the effective cap is `min(constant, width-derived available space)`. Ellipsis placement is unified on the column-aware helper's semantics — one trailing ellipsis inside the column budget whenever content is cut — which also upgrades the previously silent cuts to visible ellipses. A minimum-width floor is respected so degenerate widths degrade to a clean short/ellipsis line, never an empty or crashing render.
2. **Shared width-aware truncation helpers (prefactor).** The scattered ad-hoc truncation helpers across the touched modules collapse into one shared width-aware helper surface wrapping the terminal-UI utils plus the upper-bound `min()` rule, so every adopter gets identical ellipsis, floor, and CJK semantics. This extraction lands before the render-layer conversion.
3. **Width source and mounting: compose-in-render.** The inline mounting sites (`renderCall`/`renderResult` in the subagent tool and the batch subagents tool) stop baking fixed-capped plain strings into a `Text` at hook time; they return a component whose `render(width)` composes the lines at the real width. Width arrives through the terminal-UI `Component.render(width)` contract — the host screen re-reads terminal columns every frame, so any width-aware composition inside `render(width)` re-flows on resize for free; no manual resize subscription and no `process.stdout.columns` polling (that remains only a fallback for pure-string paths that cannot return a component). The settled collapsed branch switches its hardcoded cap-60 helper call to the width-derived cap. Streaming shapes are untouched: collapsed stays a fixed 2-line slice, expanded keeps the `STREAMING_EXPANDED_TAIL` 16-line tail cap — row-count caps are legitimate and out of the column-width story.
4. **Markdown finalize.** The settled expanded branch returns a `Container` composed of the existing header `Text` (badge + meta, content unchanged) followed by a `Markdown` component fed the full report text and the shared markdown theme (`getMarkdownTheme()`), mirroring the host chat's custom message rendering and the btw extension's message-renderer precedent. Streaming partials stay plain capped text, preserving the flicker fix (#1104). Returning a component from `renderResult` is within the SDK contract.
5. **Adjacent surfaces adopt the shared helpers.** The bottom-panel subagents section (background runs) starts consuming the width it already receives in its render signature (currently discarded): run rows and live-message quote lines truncate by column at real width. The batch subagents header's first-task preview uses the width-aware task preview (its width arrives via decision 3's component mounting). The shared row helpers (`renderActivityRow`, `renderRunRow`) and the phrase shapers behind trace lines (command first-line cap, mid-truncation, error/idle phrase caps in the tool-action-label module) gain an optional width that defaults to today's constants — upper-bound `min()` semantics apply when a width is passed — so the detached viewer's existing output and all non-width callers are byte-identical unless they opt in, while `→ Running:` lines re-flow where width is available.
6. **CJK correctness everywhere.** All truncation and wrapping routes through the terminal-UI's East-Asian-aware utilities (they already implement grapheme and wide-character width), so CJK characters count 2 columns at every converted site with no per-package wide-char dependency.
7. **Zero new dependencies.** Everything is built from the terminal-UI package (width utils, `Markdown`, `Text`, `Container`) and the coding-agent package (`getMarkdownTheme`) — both already direct dependencies of the subagent extension. No new npm packages anywhere.
8. **Backward compatibility.** The `▸`-join header structure, badge/meta shapes, streaming tail/collapsed structure, and every currently pinned unit behavior (preview caps with ellipsis, progress-line pluralization, tail-cap structure, settled content presence) remain intact; new width parameters default to today's constants so existing call sites and their tests stay valid, and explicit-width assertions are layered on top.

## Testing Decisions

Two approved test seams (user-confirmed, two-seam configuration):

- **Seam 1 — pure render functions.** The render-layer functions take an explicit width and are unit-asserted at multiple widths (e.g. 40 / 80 / 120 / 200), including CJK double-width content and ellipsis placement. Caps are asserted as **upper bounds**: at wide widths the constant binds (behavior matches today's pins), at narrow widths the width-derived cap binds and every output line's visible width fits.
- **Seam 2 — component assembly.** `renderCall`/`renderResult` (both tools) have their returned component exercised through `.render(width)` → string arrays, asserting: every line's visible width ≤ width; the settled expanded branch carries markdown theme styling (heading/bold theme codes) and the full uncapped report; streaming branches stay plain text with the 2-line collapsed and 16-line tail structure; the same component rendered at two different widths re-flows (resize behavior).

**Prior art to extend, not replace:** the subagent tool test module already pins the `▸`-join variants (agent present/absent, model segment, short-model dropping), the `taskPreview` ≤ 80 + trailing-ellipsis family, the `workIntentPreview` n=60 family, progress-line pluralization, and the isPartial / `STREAMING_EXPANDED_TAIL` structural pins; the subagent viewer test module demonstrates fixed-width `render(80)` assertions; the bottom-panel section test module pins exact row strings and the `render(theme, 100)` signature. Existing pins are kept valid via the defaulted-width contract; pins are updated only where cap semantics intentionally change (e.g. settled-collapsed cap becomes width-derived, previously bare slices gain ellipses), with the structural invariants carried through unchanged.

## Out of Scope

- Streaming-partial markdown rendering (partials stay plain capped text).
- WebUI rendering of subagent output.
- Budget/timeout behavior — owned by the separate effort `2026-08-15-subagent-dynamic-budgets`.
- Detached subagents viewer overhaul (it is already width-aware at its own layer; it only inherits the shared-helper improvements).
