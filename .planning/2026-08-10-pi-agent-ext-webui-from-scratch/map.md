## Destination

A new pi extension `bun-apps/pi-agent-ext-webui` that opens a web service port from within the extension and serves a web frontend which **coexists with the TUI on one live `AgentSession`** (same process). The web frontend can drive the agent like the TUI (prompt / steer / follow-up / abort) and renders results as **structured data** (beyond the TUI's text — diffs, patches, generated artifacts). **Agentic activity is mutually exclusive across the two frontends** — whichever side initiates a model-driving turn holds an exclusive lock; the other is blocked and shows "working…". **Pure app-logic** (direct pipeline / app execution — run.py, image/video generation, local UI ops) runs free on both sides with no lock. It is a general agent frontend, independent of `gui-movie-director`. v1 = minimal MVP (agent parity + basic mutex + generic event forwarding; rich renderers and multi-session deferred).

## Notes

- **Domain**: pi extension architecture + agent SDK. Skills every session should consult: `grilling`, `domain-modeling`, `codebase-design`, `prototype` (in `bun-apps/pi-agent-ext-wayfind/skills/`); `systematic-debugging` if a seam misbehaves.
- **Extension convention (CLAUDE.md)**: one registered entry per package — `extensions/webui.ts` (folder suffix `webui`, no `pi-` prefix). Register in exactly ONE of `manifest.json` `extensions[]` (dynamic/jiti) OR `bun-apps/pi-agent/src/static-extensions.ts` + `manifest.json` `staticExtensions[]` (compiled). Never both. Bun workspace root is `bun-apps/`; `bun install` from there; no top-level `cd` (use `( cd ... && ... )`); English for all written artifacts; `.planning/<effort>/` must be committed + pushed to `origin/main`.

- **Architecture ground truth (verified, v0.84.1)**:
  - The agent loop (`AgentSession`, `@earendil-works/pi-coding-agent`) is decoupled from the TUI — the TUI (`InteractiveMode`) is one of three run modes and owns the live session. `InteractiveMode.run()` is a cooperative `while(true)` with `await` points (NOT a blocking syscall).
  - Tool results carry structured `details` (`edit`→`{diff,patch}`, `bash`→`{exitCode,fullOutputPath}`, …) + type guards. Rich rendering is a UI task, not a protocol gap.
  - `AgentSession` is **single-driver by design** → the agentic-mutex requirement is a selfbuilt lock.

- **DECIDED (ticket 02, closed) — backbone = Path A**: one module-level `Bun.serve` (HTTP + native WS, loopback, `.unref()`-able) coexisting with the TUI loop; started lazily on the first `session_start`, kept across session switches via a module-level singleton (the extension *factory* re-runs per session, but the *module* is cached → singleton survives); `session_shutdown` drops only the session ref, the server stays. On each `session_start` the server re-points its `pi`/`ctx` to the live session. `Bun.serve` is the right primitive (native Bun, single HTTP+WS object, unref-able); the TUI uses a cooperative await loop and never conflicts with the TCP socket / stdin. Path B (CBOR `pi-server` + `pi-client` leases) is **out for v1** — in v0.84.1 the `pi server`/`pi client` CLI is a dead shell, the real server is a separate experimental lib (~3 weeks old, already breaking between patch releases), there is NO WebSocket transport, and the real TUI can't attach. Revisit once `pi-server` stabilizes + ships WS + a real `pi client`.
  - **Inbound dispatch + outbound event-mapping is a thin interface**, shaped so it could later be re-pointed at `PiServerService`/`PiSessionRuntime` (Path B) without rewriting the web client. Worth stealing from B's contract now: "authoritative snapshots; progress is transient."

- **THE agentic-mutex gate = the `input` extension event (zero patch)**: `pi.on("input", …)` fires for EVERY `prompt()` (TUI=`source:"interactive"`, web=`source:"extension"`, rpc=`source:"rpc"`) BEFORE the `isStreaming` guard; `{action:"handled"}` blocks the submission, `{action:"transform"}` rewrites it. `source` gives sibling-attribution for free. The idle-time race is closed by setting a `driver` flag **synchronously before the first `await`** in the handler (JS single-threading = atomic). The TUI already auto-routes Enter to `steer` when busy (`interactive-mode.js:2455`) as a fallback. → This single hook IS the mutex (ticket 03 designs the state machine around it).

- **RESOLVED (ticket 01, closed) — drive/observe/abort are a clean, zero-patch path**: from an extension, `pi.sendUserMessage(text, {deliverAs:"steer"|"followUp"})` injects a turn (internally calls `session.prompt()`, works mid-stream); `pi.on("message_*"|"tool_execution_start/update/end"|"tool_result"|"turn_*"|"agent_*"|"session_before_compact"|"session_compact", …)` observes the structured stream ( `tool_result`/`tool_execution_end` carry typed `.details`); `ctx.abort()` aborts. Readable state via `ctx`: `isIdle()`, `signal`, `hasPendingMessages()`, `getContextUsage()`, `model`. NOT exposed without a patch: the `AgentSession` handle itself (full `messages`, `isStreaming`, `isCompacting`) and live `queue_update` deltas (only on `session.subscribe()`, absent from the `ExtensionEvent` union).

- **Reuse map (verified)**:
  - `bun-apps/gui-movie-director` = the only `Bun.serve` site in `bun-apps/`; direct template for tickets 04/06/07 — `Bun.serve` HTTP+WS on one port + `serveWithFallback` (port..port+50 on EADDRINUSE), native WS client-set + `broadcastMessage`, `lib/origin.ts` `originAllowed` (DNS-rebinding-safe loopback Host-header guard), `lib/gui-registry.ts` + `scripts/gui-port.ts` port-discovery (FNV-hash auto-port per worktree, pid-liveness-pruned registry), `Bun.build` frontend (no vite, no committed dist).
  - `bun-apps/pi-agent-ext-web-access` = the only pi extension that hosts a listening server in-process (its `web_search` "curator": `node:http` on `listen(0,"127.0.0.1")` + `randomUUID` token + `pi.exec("open")` browser-open + watchdog idle/stale timeouts + `session_*`→`closeAll()`). webui steals its server *primitives* (token, browser-open, watchdog, lifecycle), NOT its one-shot promise-bridge (webui is a persistent co-frontend, not a tool-block-on-human). web-access is the feasibility proof.
  - `bun-apps/pi-agent-ext-btw` = the interactive-channel lifecycle pattern (structured-input → submit → filtered turn-inject). btw observes its **side** session via `AgentSession.subscribe()` (`tool_execution_*`/`turn_*`/`message_*`); its **host** `pi.on` handlers are lifecycle-only (`context`, `session_start`/`session_tree`/`session_shutdown`). The **main** agent's tool/turn events DO arrive via host `pi.on` (ticket 01), which is why webui (observing the main agent) correctly uses host `pi.on` — the TUI-overlay analogue of webui's inbound command schema.
  - No shared "local server"/"open browser" util exists in `bun-apps/` (browser-opener is duplicated in archify/obsidian) — webui writes its own and could be the first to factor it out.

- **Fact-freshness caveat**: charted while this branch was behind `origin/main`. Rebase before resolving tickets that touch pi internals.

## Decisions so far

- [01 — Live session handle & drive API](tickets/01-live-session-handle.md) — RESOLVED: driving/observing/aborting the live in-process session from an extension is a clean, zero-patch path via `sendUserMessage` + `pi.on(...)` + `ctx.abort()`; only `messages` snapshot / `isStreaming` / `queue_update` would need patches.
- [02 — Architecture backbone](tickets/02-architecture-backbone.md) — RESOLVED: **Path A** — in-process `Bun.serve` + live `AgentSession` + self-built mutex gated by the `input` event; thin dispatch seam for future Path-B migration. Reuse gui-movie-director (serve/WS/origin/port) + web-access (token/browser-open/watchdog/lifecycle).
- [03 — Agentic mutex](tickets/03-agentic-mutex-design.md) — RESOLVED (PR #1223, merged `0d45e93c`): the self-built mutex landed as a deep module — `AgentMutex` (synchronous check-and-set driver + injectable-clock watchdog) + `MutexController` adapter (verdict → `input`-event `InputEventResult` action + notifications); zero pi deps in v1 (real `pi.on("input")` + `Bun.serve` wiring is ticket 04).
- [06 — Frontend stack & delivery](tickets/06-frontend-stack-delivery.md) — RESOLVED: reframed from "frontend-stack-delivery" (React, clone gui-movie-director) to a **generic, decoupled render framework** per session decision — producers push md/html into named views via `webui.render()` (`webui_render` tool + `pi.events` "webui:render" channel); vanilla browser shell (no build, no committed dist); SSE live updates; sandboxed iframe for html; decoupled from ticket-04 chat/mutex. Stack = **vanilla, no-build**. Artifacts: `specs/06-frontend-render-framework.md`, `plans/06-frontend-render-framework-plan.md`. Spec'd + planned; EXECUTE pending.
- [05 — Rich rendering scope](tickets/05-rich-rendering-scope.md) — RESOLVED (spec'd + planned): **v1 = generic tool-mirror only; ALL dedicated renderers and binary-artifact serving deferred.** A third producer of the ticket-06 `RenderService` — `createToolMirror(registry)` subscribes the agent `tool_result` event (on `pi.on`, NOT `pi.events`; exact-name only; via the wiring's `reg()`/`disposed` guard — a SECOND `tool_result` handler alongside the verbatim outbound broadcast, additive), formats each result's typed `details` into markdown, and renders a single accumulating **"tools"** view (`mode:"md"`, replace-only registry + mirror-local rolling log). Formatting is **generic, per-toolName-aware, NO dedicated renderer**: built-ins via the SDK type guards (`edit`→fenced `details.diff`; `bash`→stdout snippet from `content` + `truncation` note + `fullOutputPath`; `read`/`grep`/`find`/`ls`→one-line metadata note, no content dump; `write`→"(no details)"); custom tools (incl. image/video-gen, narrowed by `event.toolName` string — no `isImageToolResult`/`isVideoToolResult`) → generic key-value markdown of stable `details` fields with **paths shown as TEXT** (inline code, never `<img>`/`<video>`/`<a href>`); unknown shape → truncated JSON. **Rolling cap** (last N=50 entries OR ≤ ~20000 chars, oldest dropped; over-budget single entry truncated). **Owns the 04-spec §8 `details`-shape pinning** (T2 TDD tests assert the verified SDK shapes). **D8 preserved** (pure producer — no `sendUserMessage`/`mutex_blocked`/`/ws` touch; additive to `wireWebui`; **no `WebuiHost` widening**). Deferred (v1): dedicated image/video inline preview; manifest/table renderer; diff viewer; file-tree renderer; **binary-artifact serving route**; `tool_execution_start`/`tool_execution_update` live streaming into the view; per-tool-call view tabs; client-side syntax highlighting; debouncing/batching. Artifacts: `specs/05-rich-rendering.md`, `plans/05-rich-rendering-plan.md`. Spec'd + planned; EXECUTE pending.
- [07 — Port, binding, auth & URL discovery](tickets/07-port-binding-auth-url.md) — RESOLVED (spec'd + planned): **loopback-only** (`127.0.0.1`) + the existing DNS-rebinding-safe `originAllowed` guard reused from 04 (checks Origin against Host, rejects non-loopback origins, allows absent-Origin for curl/scripts) is the security boundary; **auth = simple token-based, OPTIONAL via `setTokenAuth(token: string|null)`; `null` ⇒ no check; v1 loopback wires `null`** (loopback binding + the DNS-rebinding-safe origin guard is the boundary — the token mechanism is available but OFF). Channels `?session=` (GET+WS) / `body.token` (POST), flat `!==`, 403; the channels exist in the mechanism + are exercised by unit tests only (no shell-token injection, `RENDER_SHELL_HTML` stays a const). **port 3-tier** `WEBUI_PORT` > `PORT` > `0` (OS-assigned ephemeral; `8090`/embed-mlx-server inherently avoided by the ephemeral default + `serveWithFallback` port-walk — no special-case); **announce via `ctx.ui`** (`notify` + `setStatus`) at `session_start` (the SDK surface that reaches the TUI user), **NOT `console.log`** (debug-only, never reaches the TUI user), **NO auto-open browser** (the wiring's host interface exposes no `exec`, so it structurally cannot). Deferred (v1): wiring the token ON for loopback / server-injected shell token; persistent `appendEntry` URL row (survives `/reload`/compaction); `gui-registry`-style multi-webui discovery (`--all`/`--json`, pid-liveness-pruned); FNV-stable-per-worktree port; opt-in auto-open; remote/multi-user binding. Artifacts: `specs/07-port-binding-auth-url.md`, `plans/07-port-binding-auth-url-plan.md`. Spec'd + planned (final scope: optional token auth, OFF for loopback); EXECUTE pending.

## Not yet specified

- **Patches-gap scope**: does v1 need the full `messages` snapshot, `isStreaming`, or live `queue_update`? (Each requires a patch to expose the session handle.) The `input`-event mutex gate needs NONE of these. Sharpens inside ticket 04 — likely "no" for minimal MVP.
- **Tool-feedback convergence**: web-access's "curator" shows a tool can pop a browser surface and block on human approval. Could webui *also* host such one-shot tool-feedback surfaces later (beyond its persistent co-frontend role)? Future capability — not v1.
- **Session-tree sync**: when a web-driven turn creates a branch/fork, how does the TUI's session tree reflect it? (after 03/04)
- **Subagent/workflow rendering**: when the web triggers a `subagent`/`workflow` run, where do those render and how is the in-flight registry shared? (after 04/05)
- **Steering/follow-up queue ownership**: does the web frontend get its own pending-message queue, or share the TUI's? (after 03)
- **Multi-session web UI (tabs)**: can the web manage multiple pi sessions? Possibly v1 out-of-scope — undecided. (after 04)

## Out of scope

- Replacing or removing the TUI — destination is co-existence.
- Migrating `gui-movie-director` into webui — independent per scope decision.
- Remote (non-loopback) / multi-user access — v1 is loopback only.
- Adopting the CBOR server path (B) for v1 — too immature in v0.84.1; revisit once `pi-server` stabilizes + ships WS + a real `pi client`.
- A full app-layer rewrite — it is a general agent frontend, not a domain app.
- Mobile / responsive design.
