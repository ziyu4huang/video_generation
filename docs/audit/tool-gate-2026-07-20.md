## Summary

The Dynamic Tool Gate extension is a well-engineered piece of infrastructure — it solves a real problem (API schema token overhead) with a defensible approach (sticky activation + keyword gating). The code is thoroughly tested (65 tests covering keyword matching, gate semantics, stale-ctx guards, telemetry), well-documented with JSDoc and inline rationale, and hardened against expected failure modes (stale session ctx, malformed schemas, regex injection).

**Two findings warrant attention** — one correctness bug where `enable_tool` silently activates additional gates beyond what was requested, and one UX concern around default-on telemetry to stderr.

---

## Findings

### MEDIUM — Correctness / Defensive

#### F1: `enable_tool` unnecessarily re-evaluates all gates against `lastPrompt`

**Severity**: Medium (defensive correctness improvement)
**Status**: ✅ Fixed (2026-07-20)
**Location**: `tool-gate.ts` lines ~380–388 (enable_tool execute)

`enable_tool.execute` called `computeActiveTools(lastPrompt, allToolNames, sticky)` to recompute the active tool list after activating a gate. `computeActiveTools` re-evaluates ALL gates against `lastPrompt` — but `before_agent_start` has already fired every matching gate for that same prompt, so the re-evaluation is redundant. This unnecessarily couples `enable_tool` to the prompt-matching logic (keyword evaluation, co-occurrence) when all it needs is to filter `allToolNames` by the current `sticky` set.

In practice, the normal flow (`before_agent_start` → user prompt → `enable_tool` mid-turn) means any gate that `lastPrompt` would fire was already activated by `before_agent_start`. However, calling `computeActiveTools` here is still a latent risk — if the call pattern ever changes (e.g., `enable_tool` invoked before `before_agent_start` in a future pi version), cross-activation could become observable.

**Fix applied**: Extracted `filterActive(allToolNames, sticky)` — a pure function that computes the active list from `sticky` alone, with no gate re-evaluation. `enable_tool.execute` now uses `filterActive` directly. Also precomputed `TRACKED_TOOLS` (CORE_TOOLS ∪ all gate names) at module scope, eliminating per-call `known` set rebuilding.

**Regression test added**: `filterActive` unit tests (fail-open, sticky-only, no-mutation) + F1 regression test verifying `enable_tool({name})` does not activate unrequested gates.

### MEDIUM — API Contract & UX

#### F2: `enable_tool` response leaks implementation uncertainty

**Severity**: Low–Medium
**Status**: ✅ Fixed (2026-07-20)
**Location**: `tool-gate.ts` line ~395 (response text)

The response includes: _"They are available now (this turn if the runtime refreshes tools per iteration; otherwise on your next message)."_

This leaks runtime internals to the end user (agent). The agent shouldn't have to reason about whether tool activation takes effect immediately or on the next turn — the extension should either guarantee a specific behavior or remain silent about timing.

**Recommendation**: Shorten to `"✓ Activated: ${activated.join(", ")}. You can call them directly."` and let the runtime's actual behavior speak for itself.

---

#### F3: `enable_tool` with already-active tool reports misleading "Activated" message

**Severity**: Low
**Status**: ✅ Fixed (2026-07-20)
**Location**: `tool-gate.ts` lines ~380–395

If a user calls `enable_tool({name: "ltx"})` when LTX is already active, the code still finds the gate in `GATES`, re-adds its names to `sticky` (no-op, `Set` dedup), and responds: `"✓ Activated: ltx, ltx_help"`.

The response implies a state change that didn't happen. The `matched` filter should exclude already-active gates, similar to how `matchIntent` does.

**Recommendation**: In the `params.name` branch, filter out gates whose names are all already in `sticky`:

```ts
matched = GATES.filter((g) =>
  g.names.includes(params.name as string) &&
  !g.names.every((n) => sticky.has(n))
);
```

Then handle `matched.length === 0` with a message like `"'ltx' is already active."`.

#### F4: Telemetry always-on to stderr by default

**Severity**: Medium
**Status**: ✅ Fixed (2026-07-20)
**Location**: `tool-gate.ts` lines ~286–295 (`emitToolGateLog`)

Every turn produces a JSON line on `stderr` (or to a file if `TOOL_GATE_LOG_PATH` is set, or suppressed if `TOOL_GATE_LOG=0`). In the pi TUI, stderr lines may be visible, producing noise on every user turn.

The header comment calls this "S3-lite, baked in" — it's a lightweight analytics layer. But "opt-in" implies it should default to OFF, while the current design defaults to ON (stderr). The intent is for the developer to measure the dormant-tool miss rate, but this is an analytics concern that shouldn't leak into production sessions.

**Recommendation**: Default to silent (`TOOL_GATE_LOG=0`). Require explicit `TOOL_GATE_LOG=1` (or `TOOL_GATE_LOG_PATH`) to enable. This flips from opt-out to opt-in, which matches the comment's stated intent.

### LOW — Maintainability & Code Quality

#### F5: `computeActiveTools` had hidden mutation side effect

**Severity**: Low
**Status**: ✅ Fixed (2026-07-20)
**Location**: `tool-gate.ts` — former `computeActiveTools` (removed)

The function name `computeActiveTools` implies a pure computation, but it mutates its `sticky` parameter in place (adds newly-matched gate names). The JSDoc acknowledges this ("callers mutate it in place across turns"), but the function itself is also a caller — it mutates `sticky` internally.

**Recommendation**: ~~Either rename to `computeAndUpdateActiveTools` to signal the mutation, or split into two functions: `updateSticky(prompt, sticky): Set<string>` (mutates) and `computeActiveTools(allNames, sticky, known): string[]` (pure).~~

**Resolved**: Split into `updateSticky(prompt, sticky): void` (mutation half — fires gates, mutates sticky) and `filterActive(allToolNames, sticky): string[]` (pure half — computes the active list). The former `computeActiveTools` is removed entirely; each caller now explicitly chooses mutation (`updateSticky`) or pure computation (`filterActive`).

#### F7: `known` set rebuilt per turn inside `computeActiveTools`

**Severity**: Trivial
**Status**: ✅ Fixed (2026-07-20, as part of F1)
**Location**: `tool-gate.ts` lines ~275–276

```ts
const known = new Set(CORE_TOOLS);
for (const gate of GATES) for (const name of gate.names) known.add(name);
```

This is rebuilt on every call to `computeActiveTools` (once per turn + potential `enable_tool` calls). Since `CORE_TOOLS` and `GATES` are module-level constants, `known` could be precomputed at module load.

**Recommendation**: Move `known` to module scope:

```ts
const KNOWN_TOOLS = new Set([...CORE_TOOLS, ...GATES.flatMap((g) => g.names)]);
```

Then inside `computeActiveTools`: `allToolNames.filter((name) => !KNOWN_TOOLS.has(name) || sticky.has(name))`.

#### F8: `computeBannerSaved` double-iterates gate names

**Severity**: Trivial
**Status**: ✅ Fixed (2026-07-20)
**Location**: `tool-gate.ts` lines ~303–312

```ts
.filter((g) => g.names.some((n) => allToolNames.includes(n))) // loaded
.filter((g) => !g.names.some((n) => active.includes(n)))       // gated
```

Two chained `.some()` calls iterate the same `g.names` array. With 2–4 names per gate, this is negligible.

**Recommendation**: Merge into a single `.filter()` — minor clarity win, no performance impact at this scale.

### OBSERVATIONS — Design Notes

#### O1: CJK matching uses substring (no word boundaries)

`matchesKeyword` for CJK falls back to `String.includes()`. The comment acknowledges: _"no word boundaries without a segmenter; phrases are specific enough once bare words are removed."_ This is a pragmatic tradeoff — the co-occurrence requirement (`requires: {nouns, verbs}`) gates the risk: 下載影片 (download video) won't fire LTX because 下載 isn't in the verbs list. Validated by the Effect table tests.

No action needed at this scale, but worth revisiting if the CJK keyword set grows large.

---

#### O2: Sticky accumulates stale tool names (harmless)

When a tool is renamed or removed mid-session between `session_start` cycles, `sticky` retains the old name. This is harmless because `computeActiveTools` filters against the current `allToolNames` — a stale sticky entry never resurrects a removed tool. No cleanup needed.

---

#### O3: `krea2` gate has no `requires` co-occurrence

**Status**: ✅ Documented (2026-07-20)

Unlike `flux2`/`ltx`/`file2md`, the `krea2` gate relies solely on explicit keywords (`"krea"`, `"krea2"`, CJK: `"草圖"`, `"快速生成"`, etc.). This means generic prompts like "快速生成一個圖" would fire flux2 (via co-occurrence) but not krea2. This appears intentional — krea2's keywords are narrow enough that co-occurrence isn't needed for precision. Worth documenting the rationale explicitly.

### POSITIVE FINDINGS

These design decisions and implementation details are worth highlighting as strengths:

| Area | What's good |
|---|---|
| **Fail-open** | Unknown/unlisted tools are never gated — new extensions work immediately without updating this file |
| **Sticky activation** | Once a gate fires, it stays active for the session — prevents mid-workflow tool loss (e.g., "make it bigger" after "generate an image") |
| **Regex injection hardening** | `escapeRegExp` escapes all regex metacharacters before embedding keywords in `\b` patterns |
| **Stale session ctx guards** | `scheduleToolGateBanner` guards both the show and dismiss `setTimeout` callbacks with try/catch — prevents uncaught exceptions from crashing pi after session switch |
| **Malformed schema protection** | `measureToolTokens` wraps `JSON.stringify` in try/catch with a 0 fallback — a non-serializable tool schema never crashes `session_start` |
| **Keyword audit trail** | The S2 audit comment in `GATES` documents which bare words were removed and why — preserves design rationale for future maintainers |
| **Effect table tests** | "S2 keyword audit" test group validates 13 real-world prompt scenarios with CJK cases, false-fire checks, and cross-gate invariants |
| **Banner vs notify** | Using keyed `setWidget` instead of `notify()` prevents banner collision with other extensions (obsidian, zai-mcp) that also emit startup messages |
| **Co-occurrence design** | `requires: {nouns, verbs}` elegantly solves the "docker image" vs "generate an image" precision problem without over-engineering |
| **Banner stale-ctx tests** | Two dedicated tests verify that both the show and dismiss paths survive a session switch between scheduling and firing |

## Architecture Notes

The extension follows a sound architecture for its role (always-on, always-active extension):

- **Pure functions** (`matchesKeyword`, `gateFires`, `matchIntent`, `computeActiveTools`, `measureToolTokens`, `computeBannerSaved`, `isMissCandidate`) are exported for testability and have zero pi runtime dependency
- **Side effects** are isolated to the `toolGateExtension` closure and pi event handlers
- **Session lifecycle** is managed through `session_start` (reset state) and `before_agent_start` (per-turn evaluation)
- **Escape hatch** (`enable_tool`) is always in CORE_TOOLS, giving the agent a guaranteed path to activate any dormant tool

The per-turn pipeline is now split into two single-responsibility functions: `updateSticky(prompt, sticky)` mutates the sticky accumulator (fires gates), `filterActive(allToolNames, sticky)` is the pure read that computes the active list. `enable_tool` calls only `filterActive` — it never re-evaluates gates — which prevents the F1 cross-activation bug by design.
