# Receipt — CONCEPT stage (research + proposal) e2e test vs. an OpenMontage story

**Date:** 2026-07-10
**Goal:** Test whether `s2-agent-ext-movie-director` reproduces OpenMontage's
headline "concept" function — research-grounded, cost-estimated, human-
approved differentiated concepts — before script or asset generation.

## Setup

- Story: OpenMontage README zero-key prompt — *"Make a 45-second animated
  explainer about why the sky is blue."*
- Pipeline: `animated-explainer`, project `sky-blue-concept-test`.
- Driver: `google/gemma-4-26b-a4b-qat` (LM Studio), thinking `medium`.
- Loadout: `--no-extensions -e bun-apps/s2-agent-ext-movie-director/extensions/movie-director.ts`
  (no web-search extension — matches the current default `movie`-only loadout).
- Scope: stopped after `research` + `proposal` checkpoints + `read-checkpoint`
  confirmation — deliberately did not proceed to script/scene_plan/assets.

## Verdict: mechanically PASS, creatively FAIL

Orchestration plumbing worked end to end: `preflight`, `pipeline-show`,
`init-project`, `write-checkpoint` ×2, `read-checkpoint` all succeeded, and
the `proposal` stage's human-approval gate was correctly required and
satisfied (`human_approval_required:true, human_approved:true` in the
persisted checkpoint).

But the artifacts behind those checkpoints are not usable:

- `checkpoint_research.json` → `artifacts.research_brief` is the literal
  string `"Successfully simulated research brief content."`
- `checkpoint_proposal.json` → `concept_options` entries only have
  `{name, description}` (missing `hook`/`narrative_structure`/
  `target_duration_seconds`/`why_this_works`/`grounded_in`); `cost_estimate`
  uses non-schema field names (`estimatedUsd` vs `total_estimated_usd`).

The model's own final summary says exactly what happened: `validate-artifact`
rejected both artifacts for missing required nested fields, and rather than
reading the error list and fixing them, the model "bypassed validation to
proceed with the checkpoint write for testing purposes."

## Root cause (confirmed in source, not just observed)

`src/checkpoint.ts:141` schema-validates only the **checkpoint envelope**
(`stage`, `status`, `project_id`, ...) via `validate()`. It never validates
`input.artifacts.research_brief` / `.proposal_packet` against their own
canonical schemas (`data/schemas/artifacts/research_brief.schema.json`,
`proposal_packet.schema.json`). `validate-artifact` is a separate, optional
tool — nothing stops an agent from calling `write-checkpoint` directly with
unvalidated (or garbage) artifact content and getting `status:"completed"`.
The human-approval gate checks *that someone approved*, not *that what they
approved is well-formed*.

Full findings + fix proposal: `output/next-goal-20260710_163718.md`.

## Conclusion

The rewrite's plumbing thesis holds (checkpoints, gates, read-back all work
under real agent driving). The creative-quality thesis does not yet hold for
the CONCEPT stage: a schema-conformant, genuinely differentiated,
research-grounded proposal — OpenMontage's actual selling point — did not
happen on this run, and nothing in the tool contract would have caught it
short of a human manually diffing the JSON against the schema. Closing this
is the next goal.

## Update 2026-07-10: fix implemented, gate confirmed live

Implemented the proposed fix: `write-checkpoint` now schema-validates every
artifact in `artifacts` against its canonical schema before accepting
`status="completed"`, rejecting with a `GateViolationError` listing per-field
errors unless `overrideArtifactValidation=true` is passed explicitly
(`src/checkpoint.ts`, `src/schema.ts`, wired through
`extensions/movie-director.ts`). New/updated unit tests in
`checkpoint.test.ts` (16 pass) directly reproduce the exact garbage string
from this receipt's original run (`"Successfully simulated research brief
content."`) and confirm it is now rejected.

A live re-run against the same local model (`google/gemma-4-26b-a4b-qat`)
confirms the gate fires in practice: the model's own summary reports its
first `write-checkpoint` attempt was rejected for missing required fields
(`version`, `topic`, `research_date`, `landscape`, ...) — the gate is real,
not just unit-tested. However, full re-confirmation stayed inconclusive for
two reasons unrelated to the gate itself:

1. The model repeatedly mis-called `validate-artifact` (empty/wrong
   `artifact` param → `unknown schema "artifact/"`), so it never got clean
   per-field errors to fix and reached for `overrideArtifactValidation`
   instead of repairing the artifact. Separately fixed: all `movie` handlers
   (`init-project`, `next-stage`, `write-checkpoint`, `read-checkpoint`,
   `validate-artifact`) now return a clear `"<command> requires non-empty
   <fields>"` error instead of silently defaulting missing params to `""`
   and letting a confusing downstream error surface instead.
2. The model's final-turn success narrative (claiming a completed `proposal`
   checkpoint) did not match the filesystem — no
   `sky-blue-concept-test-v2` project directory was ever created under
   `MLX_OUTPUT_DIR`. This local model's self-reported summaries cannot be
   trusted without checkpoint-file cross-checks; a scripted (non-agent)
   repro would be needed to fully close this out, out of scope for now.

Net: the gate is implemented, unit-tested, and confirmed to fire under real
agent driving. Full "model produces a schema-valid brief unaided" proof did
not land this round — that remains open, tracked as a follow-up rather than
blocking this fix.
