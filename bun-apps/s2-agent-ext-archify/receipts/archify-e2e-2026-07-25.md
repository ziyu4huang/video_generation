## Findings

### F1 — `archify_*.execute` ignored an already-aborted `AbortSignal` (Important) — **RESOLVED**

> **Status (2026-07-25): Fixed.** Each tool now takes `signal?: AbortSignal`,
> short-circuits with an `aborted` error when `signal?.aborted`, and threads the
> signal into `runArchify`. Two new gated cases cover `archify_validate` and
> `archify_delta`. Gated suite is 14/14 green. The text below is the original
> finding, retained for provenance.

**Severity:** Important. A tool that reports a successful render after the caller has
aborted is a real correctness gap: a parent agent that aborts a run (timeout, user
cancel, plan change) will still observe a fresh on-disk artifact and a non-`isError`
result, defeating the abort contract. The wrapper silently violates the
`AbortSignal` precondition every tool in this SDK is expected to honor.

**Case (verbatim, from the gated run):**

```
151 |     const cwd = withTempCwd();
152 |     const tool = registeredTool("archify_render");
153 |     const ac = new AbortController();
154 |     ac.abort();
155 |     const res = (await tool.execute("e2e-id", { ir: JSON.parse(readFileSync(FIXTURE, "utf8")), type: "architecture" }, ac.signal, undefined, ctxFor(cwd))) as { isError?: boolean; content: { text: string }[] };
156 |     expect(res.isError).toBe(true);
                              ^
error: expect(received).toBe(expected)

Expected: true
Received: undefined

      at <anonymous> (.../__tests__/e2e.test.ts:156:25)
(fail) archify e2e — negative cases across the defineTool wrapper > an already-aborted signal never reports a successful render [157.88ms]

 11 pass
 1 fail
Ran 12 tests across 1 file. [2.72s]
```

The render completes the full pipeline (9/9 internal checks, writes the artifact,
returns a success content array with no `isError`) despite the signal being aborted
synchronously before `execute` is entered.

**Reproduction:**

```bash
( cd bun-apps/s2-agent-ext-archify && PI_AGENT_E2E=1 bun test __tests__/e2e.test.ts )
```

The failure is deterministic (observed across two prior runs by the Task 4
implementer, an independent probe, and this receipt run).

**Root-cause hypothesis** (confirmed by reading `lib/render.ts` + `lib/run.ts`):

1. `renderTool.execute(_id, params, _signal, _onUpdate, ctx)` in `lib/render.ts:93`
   names the signal parameter `_signal` (underscore-prefixed = unused) and calls
   `archifyRender(params, { cwd: ctx.cwd })` without forwarding it. The signal never
   reaches `runArchify`.
2. Even though `lib/run.ts:24` does pass `signal` on to `spawn(process.execPath,
   [...], { cwd, signal })`, that path is unreachable for the abort case because the
   wrapper never forwards the signal at all.
3. The same pattern exists in `lib/validate.ts:60` and `lib/delta.ts:55` — all three
   `execute` bodies discard `_signal`. The defect is therefore uniform across the
   archify tool surface; render is merely the one exercised by this test.

**Recommended fix** (follow-up task — out of scope for this review):

- Easiest / highest-value: short-circuit at the top of each `execute` in
  `lib/{render,validate,delta}.ts`:
  ```ts
  async execute(_id, params, signal, _onUpdate, ctx) {
    if (signal?.aborted) {
      return { isError: true, content: [{ type: "text", text: "aborted" }] };
    }
    // ... existing body, forwarding `signal` into archifyRender / runArchify
  }
  ```
- Belt-and-suspenders: rename `_signal` → `signal` in all three tool definitions and
  thread it through `archifyRender` / `archifyValidate` / `archifyDelta` into
  `runArchify(args, cwd, signal)`, and have `runArchify` attach an `'error'` handler
  to the spawned child so an already-aborted signal surfaces as a rejection rather
  than a silent success.
- Add an analogous aborted-signal case for `archify_validate` and `archify_delta`
  (the defect is uniform; the regression net should be too).
