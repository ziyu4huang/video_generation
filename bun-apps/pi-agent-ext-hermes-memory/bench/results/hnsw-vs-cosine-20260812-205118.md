# HNSW vs In-Memory Cosine — Query-Latency Benchmark

- Ticket 16 (zk-spawn) / input to ticket 14 (full-HNSW vs lazy-backfill decision).
- Date: 2026-08-12T12:56:42.073Z
- SurrealDB: `http://127.0.0.1:8000` v3.2.3 (root/root), HNSW index COSINE/F32 DIM 768.
- Vectors: synthetic 768-dim unit (Gaussian → L2-normalize), seeded. K=200 queries, TOP_K=10, EF=100.
- Client: the REAL `SurrealClient` (HTTP POST /sql, 10s timeout, 3 retries) — RTT is in the measurement.
- Build: bulk insert in 120-CREATE batches (SurrealDB /sql body capped at 1MiB ⇒ max ~143 768-dim CREATEs/body; 500/batch impossible); wall-ms recorded separately from query latency.
- Concurrent latency = per-query wall-ms from **batch dispatch** (see file header): HNSW parallelizes server-side; cosine serializes on the JS event loop.
- HNSW queries are measured at WARM steady-state: a cold-start probe (first query post-build) is recorded in notes, then a 3s settle + scale-dependent warmup (8/10/100 queries for 1k/10k/100k) precede measurement — the fair comparison to the always-warm in-process cosine.

## Crossover analysis (single-mode p95)

ratio = cosine_p95 / hnsw_p95 (>1 ⇒ HNSW faster at that scale).

| scale | hnsw_p95 (ms) | cosine_p95 (ms) | ratio | faster |

- **Crossover:** HNSW becomes faster than in-memory cosine at **100,000** vectors (single-mode p95).
- At **100,000 / 16-concurrent**: HNSW p95=48.559ms vs cosine p95=1037.260ms — HNSW **21.361×** faster (server parallelism vs JS serialization).

## Verdict

**Conclusion: HNSW holds at scale**

HNSW single p95 @1k = 10.972ms @100k = 17.958ms ; cosine single p95 @1k = 1.158ms @100k = 66.013ms.
Crossover (HNSW overtakes cosine on single p95) at **100,000** vectors.

**Implication for ticket 14:** HNSW p95 stays bounded from 1k→100k (10.972ms → 17.958ms, 1.637×) while cosine p95 climbs past it at 100,000. Under concurrency the gap widens (server parallelism vs JS serialization). **Ticket 14: build the full HNSW** — it is the scalable path; cosine remains the warm cache / fallback.
